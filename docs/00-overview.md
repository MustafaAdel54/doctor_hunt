# 00 — Project Overview

> **Doctor Hunt** — Doctor Appointment Booking App (Flutter + Supabase)
> Reference spec for AI coding agents. Read `00` → `09` in order before writing code.

---

## 1. Product Summary

A mobile application that connects **patients** with **doctors** for appointment booking.

| Role | Capabilities |
|---|---|
| **Doctor** | Pick the doctor role at signup, complete an onboarding wizard (specialization, what they treat, weekly hours, **clinic address**, optional coordinates), view/accept/reject/complete bookings, see stats and received ratings |
| **Patient** | Pick the patient role at signup, **search doctors by name or specialization**, view a doctor's free slots, **book in-app or call the clinic to confirm**, cancel own bookings, **rate the doctor after a completed visit** |

Both roles authenticate through the **same** login screen. The app resolves the role
**after** sign-in and routes accordingly.

## 2. Locked Technical Decisions

| Concern | Decision | Notes |
|---|---|---|
| Framework | Flutter (stable), Dart 3.x | null-safe, records/patterns allowed |
| Architecture | Feature-first, **two-layer** (data / presentation) — no `domain/` | client-only Supabase architecture (PostgreSQL + RLS + RPCs) |
| State management | **3 parallel branches**: Bloc+Cubit / Riverpod / GetX | see `08-state-management-branches.md` |
| Routing | **go_router** | declarative, `refreshListenable` on auth stream |
| Localization | **slang** (`slang`, `slang_flutter`, `slang_build_runner`) | EN + AR, full RTL |
| Responsive UI | **flutter_screenutil**, `designSize: Size(375, 812)` | `.w .h .sp .r` everywhere |
| Backend | **Supabase**: Auth + PostgreSQL | Supabase Plan: no Edge Functions or Storage in v1 |
| Role source | PostgreSQL `profiles` table, chosen on a role-selection screen | `'doctor'` \| `'patient'`, immutable after create |
| Maps | **deferred to v1.1** — no API key/billing yet | schema fields reserved |
| Ratings | `reviews` table + RPC aggregate | gated on a doctor-marked completed appointment |
| Theme | **light + dark**, via `AppColorsTheme` ThemeExtension | font: **Cairo** (200-900) |
| Theming | **Atomic style system** generated by `tool/generate_style.dart` → 1,425 `BuildContext` getters | `context.bold16Primary` |
| DI | `get_it` (+ `injectable` optional) on all branches | keeps branches comparable |
| Models | `freezed` + `json_serializable` | shared data+UI models (no separate entities) |
| Functional errors | `Either<Failure, T>` via `dartz` or `fpdart` | pick one, document it |

## 2A. Supabase Plan Constraints — LOCKED

The project is intentionally built for the **Supabase free tier** in v1.
The implementation must remain usable without attaching a paid billing account.

### Allowed / used in v1
- Supabase Auth: Email/Password + Google Sign-In (ID Token)
- PostgreSQL Database within the free quota
- Supabase Flutter SDK, PostgreSQL RPCs, and RLS Policies
- `slang`, `go_router`, `flutter_screenutil`, and the rest of the local Flutter stack
- `url_launcher` for phone/WhatsApp and external map links

### Explicitly excluded from v1
- Edge Functions / server-side logic
- Supabase Storage / profile-photo uploads
- Database Webhooks calling external services
- Google Maps SDK + geolocation stack (planned v1.1)

### Quota-conscious rules
- Paginate doctor and appointment lists; never fetch an unbounded table for a list UI.
- Prefer targeted queries and `limit()` values over broad listeners.
- Use PostgreSQL RPCs where atomicity is needed (booking / rating aggregate).
- Avoid polling. Use streams only for screens that genuinely need live updates.
- Seed a small demo dataset and test read/write sizes before expanding the dataset.

Supabase's free tier has specific database size (500MB) and egress limits. Treat these as hard product constraints for the demo and avoid
architectures that depend on unlimited reads/writes.


## 3. The Three-Branch Strategy (critical)

The **entire point** is a fair, apples-to-apples comparison of state management.
Therefore:

```
main                    ← shared core ONLY. No state management. No controllers.
 ├── feature/bloc       ← branches from main
 ├── feature/riverpod   ← branches from main
 └── feature/getx       ← branches from main
```

**`main` contains (identical in all branches, never diverges):**
- `apps/core/` — themes, router, session, constants, extensions, utils, shared widgets
- `generated/` — `app_colors.dart`, `style_atoms.dart`
- `i18n/` — slang JSON + generated translations
- `features/*/data/` — `models/`, `repo/` (abstract + impl), `service/`
- Pure/dumb widgets in `core/widgets/` that take data in and emit callbacks out

**Each `feature/*` branch adds ONLY:**
- the state layer (Cubits / Notifiers / GetxControllers)
- the screen-level wiring (`BlocProvider` vs `ConsumerWidget` vs `GetBuilder`)
- its own DI registration file
- its own `main.dart` bootstrap

> **Rule:** if you find yourself editing a file under `core/` or `data/`
> inside a feature branch — stop. That change belongs in `main` and must be
> cherry-picked/merged into all three.

Full workflow, git commands and merge policy: `08-state-management-branches.md`.

## 4. Non-Negotiable Coding Rules

1. **No hardcoded colors.** Ever. `AppColors.primary`, never `Color(0xFF...)` inside a widget.
2. **No hardcoded text styles.** Use the generated style atoms / active theme.
3. **No hardcoded user-facing strings.** Use `t.feature.key` from slang.
4. **No raw pixel numbers.** `16.w`, `24.h`, `12.r` — never bare `16`.
   Font sizes are the exception: `.sp` is applied *inside* the style generator, so call
   sites write `context.bold16Primary`, never `.sp`.
5. **No business logic in widgets.** Widgets render + dispatch. Application logic lives in
   the branch-specific controller/state layer, with reusable algorithms kept as pure helpers.
6. **No direct Supabase calls from presentation.** Presentation → Controller → Repository → Service → Supabase.
7. **Every async flow has 4 UI states:** `initial`, `loading`, `success`, `error`.
8. **Shared widgets are stateless & state-management-agnostic** so they survive across all three branches.
